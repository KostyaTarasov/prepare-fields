# prepare-fields

Прототип сервиса: по данным о контрольно-измерительном приборе собирает черновик карточки товара для B2B-магазина. На выходе SEO-заголовок, SEO-описание, таблица характеристик, поисковые запросы и блок для менеджера.

## Запуск

Нужен [uv](https://docs.astral.sh/uv/). Он сам поставит Python и зависимости.

```bash
cp .env.example .env && echo "вставьте LLM_API_KEY в .env" && make run
```

Дальше:

```bash
make run INPUT=examples/manometer.json FORMAT=json
cat examples/products.json | uv run prepare-fields - > cards.md
make test
make lint
```

Коды возврата: `0` всё готово, `1` ошибка входных данных, `2` ошибка конфигурации, `3` ни одна модель не ответила. Логи идут в stderr, результат в stdout, поэтому вывод можно сразу перенаправить в файл.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | основной провайдер; в `LLM_MODEL` список моделей через запятую, они перебираются по очереди |
| `LLM_FALLBACK_BASE_URL`, `LLM_FALLBACK_API_KEY`, `LLM_FALLBACK_MODELS` | резервный провайдер, подключается когда основной отказал |
| `LLM_TIMEOUT` | таймаут запроса, `60s`, `500ms`, `2m` |
| `LLM_TEMPERATURE` | температура, по умолчанию `0.6` |
| `LLM_CONCURRENCY` | сколько товаров обрабатывать параллельно |

Конфиг проверяется на старте: без ключа и моделей сервис не запустится. `.env` в `.gitignore`. `LLM_NARROW_TOPICS` остался в `.env.example` от общего шаблона и сервисом не используется.

## Входные данные

Объект или массив объектов. Обязательно только `name`:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": { "диапазон измерений": "0–1,6 МПа", "класс точности": "1,5" },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Ключи характеристик нормализуются: «диапазон измерения», «пределы измерений» и «ДИАПАЗОН ИЗМЕРЕНИЙ» сводятся к одному. Пустые значения отбрасываются и попадают в список того, что нужно уточнить. Лишние поля фида (`url`, `image`, внутренние коды) сервис не использует и в промпт не передаёт.

Примеры и зафиксированный вывод лежат в `examples/`: два блока питания ОВЕН (`result-products.md`, `result-products.json`) и манометр из ТЗ (`result-manometer.md`).

## Слои

```
cli          чтение JSON, вывод, коды возврата
usecase      сценарий карточки, порты DraftWriter и Prompts, проверка лимитов и повтор
domain       Product, Draft, Card, нормализация характеристик, лимиты ТЗ
adapters     llm (HTTP), prompts (шаблоны), json_input, render
config       env и валидация на старте
```

Зависимости идут только внутрь: `cli → usecase → domain`. Домен не знает про HTTP и про модель.

## Промпты

Лежат в `src/prepare_fields/prompts/*.tmpl`, в коде не склеиваются.

`system.tmpl` задаёт роль и восемь запретов. Главные: брать значения только из входных данных, не использовать числа, которых во входных данных нет, не выводить характеристики из артикула («-24» в названии не значит питание 24 В), при нехватке данных писать «данных нет», а не догадку.

`card.tmpl` отдаёт входные данные одним JSON-ом, отдельно перечисляет отсутствующие поля и описывает схему ответа с границами длин.

`retry.tmpl` используется при повторе: показывает модели её предыдущий ответ и список замечаний.

## Решения и компромиссы

**Таблицу характеристик собирает код, а не модель.** Модель пишет только текст: заголовок, описание, запросы, блок для менеджера. Значения в таблицу переносятся из входного JSON как есть. Это убирает главный риск ТЗ: выдумать характеристику модель физически не может, таблица не проходит через неё.

**Числа в тексте проверяются после генерации.** Из прозы модели вытаскиваются все числа и сверяются с числами во входных данных. Лишнее попадает в замечания и уходит в повторный запрос, а если и после него осталось, печатается в разделе «Проверьте перед публикацией». Проверка грубая: число в обороте вроде «в два раза» она не поймает, зато выдуманное напряжение или IP ловит.

**Один повторный запрос, не цикл.** Если черновик не попал в лимиты ТЗ, модель получает список замечаний и переписывает. Новый вариант принимается только если замечаний стало меньше, иначе остаётся первый. Два вызова на товар это предсказуемая цена, цикл до идеала на свободных тирах упирается в лимиты.

**Длина не важнее достоверности.** Когда во входных данных почти нет характеристик, модели разрешено не добирать 800 символов выдумкой. Нарушение границы попадает в предупреждения, и менеджер видит, что карточку нужно дополнить.

**Перебор моделей вместо одной.** На практике это понадобилось сразу: основной провайдер отдавал 429 по лимиту токенов в минуту, сервис дошёл до следующей модели и дособрал карточки.

**Зависимостей в рантайме нет.** HTTP через `urllib`, шаблоны через `string.Template`. Для прототипа SDK ничего не добавляет, а зависимостей и способов сломаться добавляет.

## Допущения

- Данные по двум товарам пришли строкой фида, а не готовым JSON. Я перевёл их в формат из ТЗ вручную (`examples/products.json`), сохранив все поля. Характеристик в фиде нет, поэтому карточки блоков питания показывают именно работу с нехваткой данных.
- Артикулом считаю обозначение модели из названия. Пятизначные числа из фида похожи на внутренние коды, но какое из них артикул поставщика, по двум строкам не определить, поэтому в характеристики они не попали.
- Вход только JSON: ТЗ разрешает «JSON или веб-форму».
- «Диапазон измерений» и «класс точности» помечаются как отсутствующие и для блока питания, хотя к нему не относятся. Список обязательных полей взят из ТЗ одинаковым для всех приборов.

## Ограничения и что улучшил бы

- Веб-форма. Сейчас только CLI, контент-менеджеру нужен браузер.
- При 429 провайдер сообщает `Retry-After`, сервис его игнорирует и просто берёт следующую модель. Ожидание с backoff экономило бы качество: первая модель в списке обычно лучше.
- Проверка чисел не отличает «1,6 МПа» от «1,6 кг»: сверяются числа, а не числа с единицами.
- Нет интеграционного теста на HTTP-слой: сетевой вызов не покрыт, проверяется только разбор ответа. Понадобился бы фейковый сервер на `http.server`.
- Повторный запрос один и оценивается по количеству замечаний, а не по их весу. Пустой commercial-блок и лишние два символа в заголовке весят одинаково.
- Нет кеша: повторный прогон того же товара снова платит за генерацию.
